# Port notes

Oddities found while porting Go to TypeScript (D11): Go behavior preserved as is, intentional deviations, and anything that needs orchestrator sign-off. Append only; one bullet per finding, prefixed with the ticket, e.g. `- [T5 hive] ...`.

- [T2 golden] Hive's GAMEOVER state is never observable from the game: on the tick hive enters GAMEOVER, `Game.Update` sees `GameOver()` and drops the software in the same tick, so that snapshot already has `software: null`/`sw: null` and GAMEOVER is never drawn. The last hive frame is the final FINALDEATHWAIT tick (`pauseTicks` 0).
- [T2 golden] Wave's first grid uses the pending `gridSize`, but `StepInterval` and `Layout` use `activeGridSize` (128 until Space). With pending 64 that is a 64² grid collapsing at 54 steps/tick inside a 2048² canvas (the `wave-64-seed7` frame at tick 40 is 2048² with only the top-left 1024² drawn).
- [T2 golden] Lumberjack chop direction comes from `Resolve(actionHitbox, treeHitbox)`, which keeps only the axis with the smaller overlap. Chopping from the right at x=143 shakes the tree **right** (the Y overlap wins); chopping from below at (127, 112) shakes it left. Damage is 10 per tick (only one axis is ever non-zero), 80 per swing.
- [T2 golden] Lumberjack has no world bounds: the player can walk off any edge (an early scenario draft walked to y = -30). Trees with health ≤ 0 are not drawn but still block (the diagonal walk in `lumberjack-chop` bumps the invisible tree 0).
- [T2 golden] Firefly bugs L0 and R0 start with `Duration = -durationStep*60*0 = -0`; `-0 < 0` is false, so they spawn on the first update. The entering tick's snapshot serializes `"duration":-0` (JS computes the same `-0`).
- [T2 golden] After Esc from a minigame while still facing a cabinet, the next hub tick restarts the melody and title (the player still faces Up at the machine), so `pause:start` is followed by `play:melody` one tick later.
- [T2 golden] Go hooks added for the harness (behavior-neutral, removed with the Go code in Phase 5): `internal/rng` (mulberry32) replaces every `math/rand` call in hive and wave, seeded from the clock at init; `assets.OnSoundEvent`/`assets.Silent`; `Game.UpdateWithInput`; wave's four globals became `Game` fields (`NewWithPending`, `Step`, `DrawCells`); `lumberjack.Step`/`ResetState`; firefly `entity.PatternName`; read-only `Snapshot()` methods plus `hive.Clone` for the scenario bot.
- [T2 golden] Entering a cabinet (Up+Space) sets `melodyPlaying = false` but leaves `imageTitle` set, so snapshots show `melodyPlaying: false, title: "sweet"` while inside the game and right after Esc (the title is not drawn because drawing checks `melodyPlaying`). Port the stale title as is.
- [T4 hub] Entering a machine (Up+Space) clears `melodyPlaying` but not `imageTitle` (`arcade/update.go:38-44`), so the snapshot's `title` keeps the cabinet's name while `melodyPlaying` is false, until the next melody start/stop. Preserved.
- [T4 hub] After Esc (or game over) the player is still facing Up under the cabinet, so the first hub tick back restarts the melody (`play:melody`). Esc pauses only `start`; `power`/`death`/`laser`/`boom` are left playing. Preserved.
- [T4 hub] On the Esc tick neither the software nor the hub updates (`game.go:49-53`); Esc held in the hub does nothing. Shift+P is handled first and does not end the tick.
- [T4 hub] `game.New(software)`: tick 1 is a full hub update with tick 1's input, so the player can move, start the melody or even load a different machine on that tick (which would replace the initial software after its START sound already played). Preserved.
- [T4 hub] Go `Software.Update` returns an `error` that `Game.Update` ignores; the TS `Software.update` returns `void`. `debug.Panel.x` is never read, `enabled` is always true and `Toggle` is never called; ported anyway.
- [T4 hub] `State.DebugInfo` formats with `%.0f` (ties to even); ported as `formatFloat0`. Hub positions are always integers, so it only matters in principle.
- [T4 hub] Test infra: Bun's `mock.module` leaks into every test file that runs after it in the same `bun test` process (verified on 1.4.2). The hub injects its collaborators (`new Game(software, { createSoftware, debugPrint })`) instead of mocking modules.

- [T5 hive] Collision early return kept (D11): when a bee touches the player, `PlayState.Update` returns at once (eat → PAUSE, death → DEATHWAIT/FINALDEATHWAIT). Bees later in the slice skip `updateBlue`/`updateDirection` that tick, nobody moves, no item is eaten and `resetScaredEatAwardIfNobodyScared` does not run.
- [T5 hive] Tick-order effects of `Update` (joystick, pelletAnimTick, camera, particles, state machine, popups, dials): a bonus popup is decremented on its spawn tick (first snapshot shows `ticks: 44`, so it is visible for 44 ticks, not 45); a burst's particles do not move until the next tick; a shake requested on tick N shows `[0, 0, 9, 8]` on tick N and first draws rand (two `float()` calls) on tick N+1.
- [T5 hive] Mode changes flag **every** bee to reverse, including bees still in the house; power pellets skip `home` bees. An eaten bee goes home with `home = true, dotMinimum = 0`, keeping its `reverseDirection`, `Velocity` and `Frame`, and leaves the house straight away.
- [T5 hive] `restartRound` (after a death or a win) leaves the camera, particles, items (on death) and `modeCurrent` alone; `modeIndex`/`modeTicks` reset to 0 so the next PLAY tick restarts the mode sequence at scatter. A win is detected at the start of the PLAY tick **after** the last item is eaten, after that tick's mode bookkeeping. Score and lives carry over a win.
- [T5 hive] `GameOver()` needs both `lives <= 0` and the GAMEOVER state, so the host only sees game over 121 ticks (FINALDEATHWAIT) after the last death.
- [T5 hive] Award ladder: `scaredEatAwardNext` stops at index 3, so the 4th and later bees eaten in one power period all pay 1600. It resets only at the end of a PLAY tick in which no bee has `BlueFrames > 0`.
- [T5 hive] TS structure: Go's nil checks on `s.player` are dropped (the player is always built by `restartRound` before the first `ChangeState`). The `score` field is `scoreValue` because `score()` is the `Software` method. `framesPerSecond`/`blueFramesDuration` live in `src/hive/constants.ts` (re-exported from `software.ts`) so leaf modules avoid an import cycle. Enemy identity is `kind`; `color` is kept for debug drawing. Food identity is `isFood`.
- [T5 hive] Debug-only draws (`debug = false` in Go, unreachable): `drawTile` uses `fillPremul`; `drawLines` approximates the premultiplied `RGBA{…, A:128}` with a CSS `rgba(…, 128/255)`; `drawMode` builds the Go string but does not print it (no `debugPrint` on `ts-port` when hive was ported).
- [T5 hive] `DigitReel.SyncTarget`'s `target < 0` branch (`-target % 10`) is dead code (scores are never negative); ported as is.
- [T3 engine] `Surface.fillPremul` (D15) matches Go only over an opaque destination. Over transparent pixels the "lighter" pass makes the result opaque, where Go would leave alpha `a`. Every planned use (hive particles, hub debug panel and overlay) draws over opaque pixels.
- [T3 engine] Debug primitives use a provisional pixel rule for Phase 4 to confirm against golden frames. `strokeRect(x, y, w, h)` outlines the pixels of `[x, x+w] × [y, y+h]` inclusive, so Go's `StrokeRect(x, y, w-1, h-1)` gives a `w × h` box. Edges don't overlap, so each corner blends once. `line` is Bresenham between the snapped endpoints. `fillCircle` fills the pixels whose centres fall inside the circle. None of them antialias.
- [T3 engine] `fillRect`, `fillPremul` and `clearRect` cover the pixels whose centres fall inside the rect: edges at `snap(x)` and `snap(x + w)`, which is the same rule as D13. Integer rects are unaffected.
- [T3 engine] Keyboard: when `KeyboardEvent.code` is empty, the code is derived from `key` (`"ArrowRight"`, `" "` → `Space`, `"d"` → `KeyD`, `"Shift"` → `ShiftLeft`). agent-browser's `keydown`/`press` send synthetic CDP events with `code: ""`, so without this fallback T10 could not move anything. Real keyboards always set `code`.
- [T3 engine] Loop: a frame that arrives up to 1 ms early still counts as a full tick, and the deficit carries over as negative accumulated time. This way 60 Hz rAF jitter gives exactly 1 update per frame instead of an occasional 0-then-2. The long-run rate stays 60 TPS, and the 5-update cap still discards any backlog (D2).
- [T3 engine] Parity differ: numbers compare with `===`, so `-0` equals `0`. A key whose value is `undefined` counts as absent, as it would in JSON. Everything else is exact, floats included.

- [T7 wave] Pending vs active globals at start: Go `New()` sizes the first grid from `gridSize`, but `Layout` and `StepInterval` read `activeGridSize`/`activeSeconds`, which keep their package-init values (128/5) until the first Space. In Go they are equal at init, so it never shows; with a scenario's `wave` settings (e.g. 64) the first grid is 64² inside a 2048² layout, stepping 54 times per tick, until Space applies the settings. Ported as is.
- [T7 wave] `Propogate` (spelling kept, D8) **replaces** a neighbour's set with the constraint row only when the row is shorter; it never intersects. A neighbour already narrowed to {1,2} by grass stays {1,2} next to new water. Water-beside-grass never appeared over 200 seeds of 24² full collapses (test kept), but it is not guaranteed by construction.
- [T7 wave] Go assigns the shared `constraints` row slice to the neighbour cell (`nCell.Possible = newPossible`), aliasing the table. Nothing mutates it afterwards (`Collapse` builds a new slice), so it is harmless; the TS rows are `readonly` and shared the same way. Snapshots copy them.
- [T7 wave] `tileBlack` (pattern 0) is created but the grid never produces pattern 0; kept for index parity.
- [T7 wave] Draw is incremental (intentional, render-only deviation): Go redraws every collapsed cell every frame; TS paints newly collapsed cells into a persistent offscreen surface (rebuilt when Space makes a new grid) and blits it. Same pixels; uncollapsed cells stay transparent.
- [T7 wave] Overlay vs debugui: Go's `ctx.SetScale(activeGridSize / 64)` scales the window to stay legible on the downscaled 2048+ px canvas; the HTML overlay is outside the canvas in CSS px, so it has no scale. FPS/TPS are measured by the overlay from `draw`/`step` counts over ~1 s windows (no `ActualFPS/TPS`). A slider blurs itself on `change` so Space reaches the scene.
- [T8 lumberjack] Unused assets: Go loads `Trees/Oak_Leaf_Particle.png` (`tree.go:25`) and builds `treeTrunkFrame` (frame 0,0) and `treeCanopyFrame` (frame 2,0) (`tree.go:27-28`), but never draws any of them. They are not imported or ported; only frame (1,0) is used, split into the top and bottom images.
- [T8 lumberjack] Chop damage is per tick, not per swing: every tick with `Acting && FrameX == 2` and an overlapping action hitbox costs 10 health and re-triggers `Shake` (8 ticks = 80 per swing). Health is never clamped and goes negative; a tree at health <= 0 is no longer drawn but still blocks the player and can still be chopped (and shaken, invisibly). Ported as is.
- [T8 lumberjack] `Tree.Behind` is just `player.Y < tree.Y + 16`, with no X check, so every tree in the row flips to "behind" (drawn over the player) at once. Only `Transparent` checks X. Ported as is.
- [T8 lumberjack] Up+Down held together: the Y moves cancel out, but `Moving` stays true, so the walk animation plays in place, facing DOWN (the last direction applied), and Space can't start a chop. With a horizontal key added, speed drops to the diagonal 1.5 px/tick. Ported as is.
- [T8 lumberjack] Out-of-range `Spritesheet.Frame` returns nil in Go, and `DrawImage(nil)` would panic. It can't happen with the current sheets (body max FrameY 34 of 56, tools 0..2 of 12). TS `mustFrame` throws instead.
- [T8 lumberjack] Layout: game.go's `const` block (`debug`, `width`, `height`, `tileWidth/Height`, `scale`) lives in `src/lab/lumberjack/constants.ts` instead of `game.ts`, so `tree.ts`/`player.ts` can import it without an import cycle. `thetaMax`/`thetaInterval` are hard-coded literals equal to the values Go folds at compile time (checked in `tree.test.ts`). Debug hitbox drawing (`debug = false` in Go) uses `fillPremul` on a snapped rect; it is never drawn.

- [T6 firefly] Bullets flagged dead at `y <= 0` (they are 0×0, so `Height/2` is 0) still collide on that same tick: the collision loop (`game.go:167-183`) does not skip `Dead` bullets. Preserved.
- [T6 firefly] Bugs that have not spawned yet (`Duration < 0`) sit at (0,0) and are collidable (only `DeadFrames` is checked). A bullet near the top-left corner can kill a waiting bug. Preserved.
- [T6 firefly] The first bug of each side gets delay `-durationStep*60*0`, which is `-0`; `-0 < 0` is false, so it flies on the very first update. Same in JS. `-0` never reaches a snapshot (the first update adds `durationStep`).
- [T6 firefly] Explosion column is `5 - trunc(deadFrames/15)`: column 0 is never shown (75 is decremented on the tick it is set), and for `deadFrames` 1..14 column 5 is off the 160 px sheet, so the empty sub-image draws nothing. The exploding bug is invisible for its last 14 ticks but still holds up the wave respawn. Preserved.
- [T6 firefly] Player X clamp is asymmetric: `[8, 217]` (`224 - 8 + 1`). Preserved.
- [T6 firefly] A bug flying off the top is culled from drawing at `y <= 0` but only removed at `y < 0`; dead bugs are removed at the end of the tick, so one snapshot shows `bugs: []` before the next update respawns the wave.
- [T6 firefly] `debug.go` (unreachable, `debug = false`): `colorControlLine` is premultiplied `RGBA{255,255,0,128}`, which `Surface.line` (CSS colour) cannot express exactly; ported as `rgba(255,255,0,0.5)`. Dead code, no parity impact.
- [T6 gearhead] Holding only Up or Down still walks: `Moving()` is true and the gnome moves 1 px in its current facing. Direction priority (Up, Down, Left, Right) also means Up+Right does not turn the gnome right. Preserved.
- [T6 gearhead] `Frame += 0.2` drifts in float64: frame 2 starts on tick 11 (not 10), frame 3 on tick 15, and the wrap (`>= 4`) happens on tick 20 at `4.000000000000001`, so the walk cycle is uneven. Same arithmetic in JS; preserved.
- [T6 gearhead] Y never changes (240) and X is clamped to `[6, 108]`, so the gnome only walks the left half of the 224 px workshop. Preserved.

- [T11 explore] The T9 Space quirk comes from the key name, not the timing. `agent-browser keydown Space` sends `key: "", code: ""`, so the game sees nothing. `keydown " "` sends `key: " ", code: ""`, and the `key` fallback maps it to `Space`. - [T11 explore] Integer scaling checks (pixel-block check on screenshots: every logical pixel is a uniform k×k device block). At 1280×800 the hub is 4×, firefly/gearhead/lumberjack 2× and hive 1×. Hive is 336×428 and 2× = 856 > 800, so D1 picks k = 1 and hive looks small on an 800 px tall window. That is per spec, but it might be worth a UX follow-up. At 1920×1080 the hub is 6×, gearhead/firefly 3× and hive 2×. Wave uses the fractional downscale (2048² → 800² CSS px) with no blended colours. Every block is uniform after every enter, Esc and Shift+P resize. `imageSmoothingEnabled` stays false and `image-rendering: pixelated` is set.
- [T11 explore] At device scale factor 1.25 (1280×800) the hub (5×), firefly and gearhead (3×) are crisp, and every interior pixel is a uniform block in every scene. The outermost device row or column is off by one in two scenes:
  - Hive (2×): the **bottom logical row** is 1 device px tall instead of 2 (855 device rows, not 856).
  - Lumberjack (3×): the **last logical column** is 1 device px narrower (1535 device columns, not 1536), and one extra device row of grass appears at the top.

  Cause: the CSS size `k*logical/dpr` (537.6×684.8, 1228.8×691.2) can't be represented in Chrome's 1/64 px layout units (684.8 becomes 684.796875 = 855.996 device px). Firefly and gearhead have the same fractional sizes but a transparent 16 px buffer at the edge, so nothing visible changes. Cosmetic, 1 device px, only at fractional DPR. Possible fix in `src/main.ts` `present()`/`fitScale`: round the CSS size up to the next 1/64 px, and maybe the centring offset too.

- [T10 frames] Result: all 50 golden frames match at 0 differing pixels (pixelmatch threshold 0.1), with no mask needed: hub incl. debug panel and overlay, gearhead, firefly, wave, hive incl. particle frames, lumberjack incl. the rotated tree top. Byte for byte, only alpha-blended pixels differ, by ±1 per channel (hive particles in `hive-clear/387`, the half-transparent lumberjack tree in `lumberjack-chop/556`/`561`), plus one rotated tree-top pixel in `lumberjack-chop/108`. No particle was off by a pixel, so no last-ulp `Math.sin/cos` exception is needed. Rerun with `bun run frames` then `bun run frames:report`, which writes `out/frame-report.md` and masks lumberjack's rotated tree-top edge pixels (`scripts/tree-mask.ts`, derived from the trace snapshot).
- [T10 frames] D13 corrected: half rounds **up**. `snap(v)` is now `Math.floor(Math.fround(v) + 0.5)`, not `Math.ceil(v - 0.5)`. Ebitengine passes every `DrawImage` vertex through `adjustDestinationPixel` (`internal/graphics/vertex.go`), which moves a fraction in [1/2, 13/16) to 11/16, so the first covered pixel centre is `floor(v + 0.5)`. The GeoM is float64 but goes into the vertex buffer as float32, hence the `fround`. Firefly (the canary) never hit an exact `.5`. Hive did (`y = 99.5`, `243.5`, `135.5`, `x = 209.5`, `19.5` in `hive-clear/601`, `9683`, `hive-highscore/3042` and `hive-modes/3358`), and so did lumberjack's 1.5 px/tick diagonals (`556`, `561`). With `ceil(v - 0.5)` those sprites landed one pixel up or left. `fillRect`/`fillPremul`/`clearRect` edges use the same `snap`.
- [T10 frames] Rotated draws now place the quad corners where Ebitengine does instead of using the exact affine. `Surface` builds the GeoM in Go's order and precision (float64, then float32), runs the three corners (0,0), (w,0), (0,h) through `adjustDestinationPixel`, and sets the canvas transform that maps the source onto them. Canvas nearest sampling at pixel centres then picks the same texels as Ebitengine's GPU. With the exact affine, the tree top at `lumberjack-chop/108` (theta 0.0305) differed on 115 pixels: whole texel seams inside the canopy, not just edges, so an edge mask could not have covered them. Ebitengine splits the quad into two triangles, and the fourth corner can sit a fraction of a pixel off the canvas parallelogram; the golden frames do not show this. `Rotate(0)` is a no-op in Go, so `angle: 0` is a plain snapped draw.
- [T10 frames] `fillPremul` over a transparent destination is now exact for valid premultiplied colours (every component ≤ `a`): it is a single source-over fill of the straight colour `rgb(r·255/a, …)` at alpha `a/255`, which keeps alpha `a` the way Go does. The hub debug panel `{20,20,20,200}` hangs over the transparent +120 strip, and the old black-then-"lighter" path made it opaque (10,372 differing pixels in `arcade-walk/390`/`410`; now 0, byte-exact). "Invalid" colours (a component above `a`: hive particles, the hub overlay `{0,255,0,64}`) still take the black + "lighter" path, which is exact only over opaque pixels. Every such draw is over opaque pixels, so nothing in the golden frames is affected.
- [T10 frames] Debug primitive pixel rules: `strokeRect` (the hub overlay, `StrokeRect(x, y, w-1, h-1)` → a `w × h` outline, each corner blended once) is confirmed byte-exact by `arcade-walk/390`/`410`. `line` and `fillCircle` are only called from unreachable debug code (firefly `debug.go`, hive `drawLines`, both `debug = false`), so no golden frame covers them and their provisional rules stay unverified.
- [T12 cleanup] The T11 fractional-DPR off-by-one (hive 855 device rows, lumberjack 1535 columns plus an extra top row) is an artifact of agent-browser's `set viewport <w> <h> 1.25`, i.e. CDP device-metrics emulation, and not of the game. Under emulation Chrome snaps layout to whole **CSS** px and then scales the raster. A plain red `<div>` at `top: 57.6px` has half-covered first and last device rows (72.5 to 927.5), and the canvas comes out 684 CSS px = 855 device px tall whatever CSS size is set. Rounding the size up to the next 1/64 px, or placing the canvas absolutely at an integer device offset, changed nothing there. Launched with a real `--force-device-scale-factor` (headless Chrome for Testing 151, driven over `agent-browser --cdp`), the unchanged `fitScale` + flex centring is exact. At 1280×799 CSS (1600×999 device) with DSF 1.25, and again with DSF 1.5 (1920×1199), every device pixel inside and in a 1 px ring around the canvas matches the logical frame upscaled ×k on black (0 mismatches) for the hub, hive, firefly, gearhead and lumberjack. The 999/1199 px heights also cover half-pixel centring. Rounding the CSS size up to 1/64 px made things **worse** on a real DSF: at half-pixel centring the bottom edge rounded the other way and hive painted 857 rows, with one logical row 3 device px tall. So `fitScale` stays `k * logical / dpr`, pinned by a unit test. Verify DPR behaviour with a real device scale factor, not `set viewport ... <scale>`.
